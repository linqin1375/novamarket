# NovaMarket 设计与改造记录

## 事实与边界

单实例营销权益演示系统，库存支持 Redis / 内存，账本使用 JDBC。本机部署为真实 Redis + H2 文件库。消息总线在进程内运行，模拟权益存于数据库；不接真实支付，不宣称分布式高可用。

## 1 请求幂等绑定业务身份

requestId 是全局唯一的业务请求键，绑定 activityId 与 userId。数据库命中后先核对绑定，再返回已有结果；该步骤在活动时间和入口限流之前，让活动结束后的原请求仍能查询结果。

数据库没命中而缓存存在未结算预扣时，返回 PROCESSING。跨身份复用返回 IDEMPOTENCY_CONFLICT / HTTP 409。唯一索引是数据库的最终防线，缓存主要减少重复工作。

## 2 缓存原子操作

内存实现用同一个 monitor 包围身份检查、分片查找、用户额度、库存变化、幂等结果与预扣记录写入。代价是内存扣减阶段会串行，不用这组结果宣称 Redis 性能。

Redis 通过 Lua 操作全部库存分片、用户额度和请求记录。首选用户哈希分片没库存时探测其他分片，避免“总库存还有一件但该用户分片为零”被误判售罄。落库和回滚使用实际命中的分片。

此实现为 standalone Redis；键没有按 Cluster 槽位设计。Lua 的原子执行不等于遇到运行时错误能自动回滚先前写入；应用控制数据结构类型、参数长度，并由数据库条件更新、预扣记录和对账兜底。不能据此承诺任意 Redis 数据损坏场景都能自愈。

## 3 预扣记录与原子回滚

预扣记录包含 requestId、activityId、userId、claimNo、shardNo、毫秒时间。未结算记录不设置 TTL，防止长时间故障使回滚凭据消失。幂等缓存仍有 TTL，待结算记录保留身份元数据，过期后的原请求仍会识别为重复。

回滚脚本仅在请求自己的预扣记录存在且活动、用户匹配时执行：归还真实分片库存、减少用户计数、删除请求记录和索引在同一调用内完成。不能仅凭用户“总领取数大于零”判断某请求可回滚，否则已成功请求或第二次回滚会错误归还库存。

数据库提交后清理预扣记录；该请求从此不能用回滚接口归还库存。提交报错时先查询数据库是否已经提交，无法查询则保留预扣等待恢复，避免把已提交库存盲目加回。

## 4 本地事务与数据库限领

ClaimSettler 独立 bean 的事务同时处理 user_quota 条件更新、stock_shard 条件扣减、claim_record 唯一领取单及 local_message 待办。任一步失败整体回滚，不额外手动补数据库库存。

user_quota 使用活动、用户联合主键及 claimed < limit 的条件更新。即使缓存计数丢失，数据库仍能拦截超限，并回滚缓存本次预扣。事务框架的代理生效边界通过独立服务调用实现。

## 5 受理与发奖分离

PROCESSING / HTTP 202 只代表领取已经受理。SUCCESS 只在发奖记录与领取状态已经提交后返回。客户端用 claimNo 查询或复用 requestId 重试。

GrantService 在事务中锁定领取单，只对 PROCESSING 状态发奖。benefit_grant.claim_no 唯一索引防止重复记录，随后更新 SUCCESS 与本地消息 CONFIRMED。重复投递补齐确认；失败或已回滚领取单不能被消息错误发奖。

重投成功也增加退避计数，防止“发出去了但一直不消费”的消息无限热循环。达到上限标记 DEAD；人工处理的前提是检查数据库事实，而非直接重新扣库存。

## 6 单实例维护栅栏与分片对账

领取持有读锁，维护持有写锁。正常领取之间仍可并发；修正缓存时等待缓存预扣、数据库结算及清理完成。仍有未结算记录时跳过该活动的强制修正。

对账比较每个分片，不能只比较总和；总量都是 16 而分布分别为 [16,0,...] 与 [2,2,...] 仍是错账。修正库存时同时重建用户限领。

维护锁只在本进程有效；多实例需要外部协调、租约或数据库围栏等完整方案。本项目未将本地锁包装成分布式一致性。

## 7 启动恢复

Flyway 负责一次性建表和后续版本演进；local profile 使用 H2 文件库、WRITE_DELAY=0。

启动恢复在 Web 服务准备好之前执行，按数据库已提交的 PROCESSING / SUCCESS 领取单重建用户额度与库存。未提交的缓存预扣会被清理。持久化本地消息留在库内，由补偿任务重投。数据库仍是恢复事实来源，旧缓存不能单独代表领取成功。

## 8 可复现实验

默认 25 个测试与可选 5 个 Redis 测试。真实进程验收额外检查：投递失败产生 PROCESSING、重启 Java 与 Redis、恢复发奖、复用原请求、限领持久化、冷内存缓存恢复，以及切回 Redis 后的分片对账。

性能工具以固定请求数和完整时段统计。受理数量、售罄、限流、HTTP 错误、最终发奖数分开记录。较高的“请求吞吐”可能主要来自售罄或限流响应，不能等同于权益发放吞吐。
